Every few years something new promises to replace the humble static site,
and every few years I end up back here anyway. Not out of stubbornness —
out of noticing what actually breaks in production versus what just sounds
impressive in a pitch deck.

A static site has a refreshingly short list of failure modes:

1. The build fails (you find out immediately, before anyone sees it).
2. The CDN is down (not your problem, and rare).

That's basically it. No database connection pool to tune, no server to
patch, no origin to fall over under load. The entire site is just files,
and files are boring in the best possible way.

## Where this one lives

This blog is generated by Jekyll, built by GitHub Actions on every push, and
served by GitHub Pages. The whole pipeline is:

> write Markdown → push to `main` → Actions builds the site → Pages serves
> the static output from a CDN

No server I have to think about ever again. If GitHub Pages disappeared
tomorrow, the entire site is still just a folder I could drop onto any
static host in five minutes — Netlify, Cloudflare Pages, an S3 bucket,
whatever. That portability is the real feature.

## What I'd still reach for a framework for

I'm not dogmatic about this. If a project needs real interactivity, user
accounts, or data that changes per-visitor, I'll happily reach for something
with a server behind it. But a blog isn't that. A blog is prose that
occasionally needs a dark mode toggle, and static tooling has that covered
without breaking a sweat.
